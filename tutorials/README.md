## Conformance notes

- **Standalone carrier (ST1–ST6):** the primary path performs no clone, repository install, or repository import. Section 2 carries `src/tirex_forecasting_pipeline/` verbatim — `evaluation.py`, `validation.py`, `pipeline.py` in dependency order, each cell tagged `metadata.dimer.embedded_module`; the only rewrites make the default weights directory working-directory-relative and remove the package-relative `from .x import` lines (the names are kernel globals). Section 3 carries the model identity and the 3-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the generating revision, the modules and their concatenated SHA-256, and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when any carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition:** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries that are absent (`README.md`, `model-config.yaml`, `model.ckpt`), from the Hugging Face Hub at the immutable revision (never `main`); `verify_snapshot` re-hashes every entry; `from_pretrained(weights_dir=WEIGHTS_DIR)` hands the verified directory to `tirex2.load_model`, which reads the two loader files from it directly. The checkpoint is a PyTorch `.ckpt` deserialised by upstream `tirex2` with `weights_only=True`; the trust boundary is the digest-verified file at the pinned revision (see `../docs/WEIGHTS.md`).
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/tirex_forecasting_input_manifest.json` with the schema, ceilings (`MIN_CONTEXT`, `MAX_CONTEXT`, `MAX_HORIZON`), per-variate observations, verdict, and one recorded rejection finding (a too-short context); `evaluation_report` (EVAL21) writes `outputs/tirex_forecasting_evaluation_report.json` — `sample-sanity` with `mae`, `rmse`, `interval_coverage` (q10–q90) and the `last_value_baseline` on the chronologically withheld truth, `not-measurable` (with what would make the task measurable) when no truth is supplied.
- The default sample is a deterministic synthetic trend + seasonal series generated in code (no download); its metrics are sanity evidence for the input contract, the holdout plumbing and the forward pass, not a correctness or benchmark claim.
- Forecasting obligations (Notebook Specification §20.3): chronological order is preserved, the final horizon is withheld, no future target reaches the model, horizon and effective context are printed, q=0.5 is stated to be a model median, the other quantiles are described as model quantiles rather than confidence intervals, and the last-value baseline is compared on the same holdout.
- CPU is the reference path because upstream CUDA execution compiles fused recurrent kernels on first use and needs a CUDA toolkit; the notebook does not assume a GPU.
- BYOD CSV headers are inspected before pandas ingestion so duplicate columns cannot be silently renamed; timestamps must be unique, increasing and regularly spaced. `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
